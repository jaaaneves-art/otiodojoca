## 3. Aplicado em produção

### 3.1 Exposição de emails — corrigida

`profiles` tem uma coluna `email` preenchida (44 de 44, consistentes com
`auth.users`), e a policy `"Perfis publicos visiveis para todos"` é
`USING (true)`. Como a RLS filtra linhas e não colunas, qualquer pessoa
com a chave publicável — que está no JavaScript do site — lia os
endereços todos sem ter conta.

Confirmado com pedido real à API REST, antes e depois:

```
GET /rest/v1/profiles?select=username,email
antes:  200 · [{"username":"0828","email":"0828@superloja.com"}, ...]
depois: 42501 · permission denied
```

Correção: `REVOKE SELECT ON profiles FROM anon, authenticated` seguido de
`GRANT SELECT` por coluna, excluindo `email`. Nenhum ficheiro do projeto
faz `select('*')` em `profiles` nem lê essa coluna, por isso nada partiu.

### 3.4 Escutismo — Fase 1 completa

**DEC-4 resolvida:** base v1 + pipeline de fotografias portado do v5.

Apareceu durante a sessão um `escutismo-schema-v1.sql` produzido por
outra sessão, com desenho diferente do v5 que estava preparado. Corria
limpo e tinha melhor estrutura organizacional — `escutismo_associacoes`
como tabela (suporta CNE, AEP, ER, AGP), aprovadores genéricos com
constraint de unicidade, recibos de leitura. Mas não tinha nada sobre
fotografias, que era requisito explícito.

Decisão: v1 como base, com um patch que acrescenta o pipeline de fotos
do v5 e corrige duas coisas encontradas ao lê-lo:

- **`e_menor` desatualizava-se.** O trigger era `BEFORE INSERT OR UPDATE
  OF data_nascimento`, e a data de nascimento nunca muda — quem entrava
  com 17 anos ficava menor para sempre. Ao mesmo tempo a função
  `escutismo_e_menor()` calculava ao vivo: duas fontes a discordar, com
  as CHECK a usarem a coluna e as policies a usarem a função. Acrescentada
  a view `escutismo_membros_v` com `menor_agora` calculado, e a função
  `escutismo_atualiza_menoridade()` agendada no pg_cron às 03h.
- **Escalões fixos numa federação.** O CHECK tinha cinco nomes hardcoded
  num schema que existe para suportar várias associações. Passam a vir de
  `escutismo_associacoes.escaloes`, validados por trigger.

**DEC-1 resolvida sem decisão:** o v1 já usa **18 anos** para tudo, que
é o limiar conservador que tinha sido sugerido para o direito à imagem
(art. 79.º do Código Civil). Um limiar só, em vez de dois.

Estado final: 11 tabelas, 19 policies, 11 funções, view, 2 constraints de
proteção de menores, 2 buckets de Storage com 4 policies, cron agendado.

**Convenção de caminhos no Storage:** os ficheiros têm de ser guardados
como `<agrupamento_id>/<nome>.jpg`. As policies usam o primeiro segmento
para saber a que agrupamento a foto pertence. Um ficheiro na raiz fica
inacessível a toda a gente, sem erro a explicar porquê.

### 4.1 `params` como Promise (Next 16.3.1)

Quatro rotas dinâmicas acediam a `params` de forma síncrona. O sintoma
era 404, não um erro: a página rebenta ao ler `params.id` e o Next
devolve 404.

`app/perfil/[id]`, `app/mercado-da-terra/editar/[id]`,
`app/agenda-agricola/plantacao/[id]`, `app/(freguesia)/freguesia/[slug]`

O grep inicial deu ~100 resultados, quase todos falsos positivos: nas
páginas de listagem o `params` é variável local vinda de um
`await searchParams` feito acima. O filtro que separou:

```bash
grep -rn "params: *{" app --include=page.tsx --include=layout.tsx --include=route.ts
```

### 4.2 Páginas de edição sem link

Existem cinco rotas `editar/[id]` (mercado-da-terra, gran-bazar, imoveis,
lup, viaturas). Todas funcionam. **Nenhuma estava ligada à interface** —
quem publicava um anúncio não o conseguia corrigir, em módulo nenhum.

Feito o Mercado da Terra: o cartão deixou de ser um `<Link>` inteiro (um
link dentro de outro é HTML inválido) e ganhou uma barra de ações com
"Editar" e "Ver anúncio". Os outros quatro ficam por fazer.

### 4.3 `details` NOT NULL

Ao abrir a página de edição pela primeira vez, o formulário gravava com
erro: `null value in column "details" violates not-null constraint`.

A coluna tem `DEFAULT '{}'` mas o código enviava `null` explicitamente
quando não havia campos — e o default só se aplica quando a coluna é
omitida, não quando lhe passamos `null`. Corrigido para enviar `{}`.

## 6. O que custou tempo, e porquê

### O SQL Editor engole scripts em silêncio

Quando um script cria tabelas, o Supabase pergunta "Run with/without
RLS". Enquanto não se responde, o script **não corre** — e a verificação
a seguir devolve zero, sem erro nenhum. Perdeu-se mais de uma hora a
diagnosticar um script que nunca tinha sido executado.

Para DDL, usar o psql:

```bash
read -rsp "Connection string: " SUPA_URL; echo
echo "$SUPA_URL" | sed 's/:[^:@]*@/:***@/'   # confirmar antes de correr
psql "$SUPA_URL" -v ON_ERROR_STOP=1 -f ficheiro.sql
unset SUPA_URL
```

O `ON_ERROR_STOP=1` mostra o erro na linha exata. O editor não mostra.

### Bracketed paste corrompeu comandos

Apareceram `^[[200~`, `\ \`, e duas linhas coladas juntas. Um caso foi
grave: um `wget -O-` com a linha corrompida escreveu para ficheiro em vez
de stdout e deu uma **confirmação falsa** de que os emails estavam
fechados quando não estavam.

Escrever à mão os comandos curtos. Verificar sempre com um segundo
método independente.

### Correr o mesmo `sed` duas vezes

Duplicou `const { id } = await params;` e o Turbopack falhou com
`the name 'id' is defined multiple times`. Confirmar com `grep -c` antes
de compilar.

### Três diagnósticos meus que estavam errados

- **Freguesias.** Previ que o script original apagaria o Módulo Freguesia
  ao ativar RLS sem policies. Testei contra um stub sem policies; na base
  real `freguesias` já tem leitura pública. Inofensivo.
- **`profiles.email`.** Disse que a coluna não existia, por extrapolar da
  regra do projeto em vez de verificar. Existe, preenchida e consistente.
- **Privilégios `anon`.** Alarmei-me com `anon` a ter INSERT/DELETE/
  TRUNCATE em ~50 tabelas. É o comportamento por omissão do Supabase, que
  apoia a segurança na RLS e não nos GRANTs.

Nos três casos o erro foi o mesmo: inferir em vez de verificar. É a mesma
falha que produziu o SQL que não corria.
