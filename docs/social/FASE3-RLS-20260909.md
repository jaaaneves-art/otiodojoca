# Módulo social — Fase 3: RLS

**Data:** 2026-09-09
**Estado:** código e testes preparados; migration ainda não aplicada à produção.

## Falhas encontradas e corrigidas

- A RPC de conversas diretas aceitava dois utilizadores arbitrários. Agora uma
  sessão normal tem obrigatoriamente de pertencer ao par e não pode conversar
  consigo própria.
- As policies de membros consultavam `group_members` a partir da própria tabela,
  com risco de recursão RLS. Foi criado o helper protegido
  `is_group_manager(uuid)`.
- O criador de um grupo não era inserido atomicamente como membro `owner`.
- A API permitia `UPDATE` geral em mensagens apesar de a regra declarar apenas
  soft delete. Agora só a coluna `deleted_at` pode ser alterada pelo autor.
- Um utilizador conseguia tentar entrar numa chamada alheia conhecendo o UUID.
  A entrada e a saída exigem agora participação na conversa correspondente.
- `owner_id` do grupo deixou de poder ser transferido por um `UPDATE` comum.
- Todas as funções `SECURITY DEFINER` deste módulo passaram a fixar
  `search_path = ''`; as funções exclusivas de trigger deixaram de ser
  executáveis por `PUBLIC`.

## Cobertura

- `tests/social/rls-policy.test.mjs`: 7 verificações estruturais rápidas.
- `supabase/tests/database/social_rls.test.sql`: 31 verificações pgTAP com quatro
  utilizadores, duas conversas privadas, mensagens, chamadas e um grupo.
- A suíte Vitest geral continua verde: 114 testes.

## Validação antes de produção

Executar numa máquina com Docker e Supabase local:

```bash
npx supabase db reset
npm run test:social-rls:db
```

Só depois dos 31 testes pgTAP passarem deve a migration
`20260909120000_social_module_phase3_rls.sql` ser aplicada à produção.
